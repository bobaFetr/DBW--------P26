# План за защита на текущия статичен сайт

Начална дата: 27.10.2026 г. Период: ноември 2026 — април 2027 г.
Отговорник: собственикът на проекта. Часова зона: Europe/Sofia.
Това е график за изпълнение, а не активирана автоматизация или постоянно наблюдение.

## Какво може да остане тайно от REA

Изискването „нито един ред код да не е достъпен“ е несъвместимо с публичен уебсайт.
Браузърът получава HTML, CSS, JavaScript и публичните изображения. Посетителят може
да ги запази и анализира с REA, DevTools или друг инструмент. Минифицирането не е
криптографска защита. Липсата на source maps затруднява възстановяването на оригиналния
frontend, но не скрива изпратения код. SSR също изпраща HTML и не скрива видимия дизайн.

Постижимата цел е: оригиналните непублични файлове, Git историята, локалните настройки,
ключовете, паролите и административните функции да не се публикуват. Разглеждането или
копирането на frontend не трябва да дава право за промяна на истинския сайт.

Ако изобщо не трябва да има анонимен достъп, сайтът трябва да стане частен зад вход
на ниво хостинг/identity gateway. Това ограничава аудиторията и търсачките; допуснат
потребител пак може да анализира полученото. Такава промяна не е приложена.

## Изходно състояние

- Next.js static export; Render публикува само `out/`; няма production API/база.
- `npm run build` използва `scripts/build-static.cjs`: принудително bundled content,
  изключени admin и local API overlay, премахнати admin HTML и отделният му JS bundle.
- Проверка преди/след build блокира неодобрени типове/пътища, symlink файлове,
  source maps и избрани разпознаваеми credential patterns. Това не е пълен secret scanner.
- Production browser source maps са изключени; CSP блокира API връзки и inline scripts.
- След локалните поправки: 60 frontend теста, lint и build преминаха; npm audit отчете
  0 известни уязвимости тогава. Резултатът не е постоянна гаранция.
- Поправките са в workspace; публикуването им и настройките на реалния хост не са потвърдени.

## Първо изпълнение — преди следващото публикуване

- [ ] Включи MFA за GitHub, Render, регистратора и имейла за възстановяване. Запази recovery
  кодовете офлайн; не ги слагай в проекта. Прегледай активните сесии и сътрудниците.
- [ ] Потвърди, че хранилището е private, ако изходният код не трябва да е публичен.
  Това не скрива frontend bundle. Прегледай разрешенията на GitHub Apps/deploy tokens.
- [ ] Изпълни цикъла по-долу и публикувай проверения commit чрез нормалния Render процес.
- [ ] Потвърди от deployment log: `npm ci && npm run build`, publish directory `out`,
  admin disabled и успешни artifact checks. Не заменяй командата с директно `next build`.
- [ ] Провери live сайта и всички алтернативни provider/custom домейни по секцията по-долу.
- [ ] Включи известия за нови зависимости/уязвимости (например Dependabot), не автоматично
  сливане без проверки. Не добавяй tokens в workflow, issue или публичен build log.

## Безопасен цикъл за обновяване

Работи от корена на проекта в PowerShell, в отделен branch и без да изтриваш чужди промени.
Първо прегледай `git status` и запази работата си в подходящ commit/backup.

```powershell
git status --short
npm.cmd ci
npm.cmd outdated
npm.cmd audit
npm.cmd audit --omit=dev
```

`outdated` и `audit` могат да върнат nonzero код за намерени обновления/уязвимости.
Прочети advisory и changelog; обновявай целево съвместими версии. За пакетите с точни
версии и `overrides` прегледай `package.json` изрично — `npm update` не решава всичко.
Дръж `next` и `eslint-config-next` съгласувани; провери React peer dependencies.
Не използвай сляпо `npm audit fix --force` и не изключвай TLS проверките.

След целевите обновявания и актуализирания `package-lock.json`:

```powershell
npm.cmd ci
npm.cmd run test:frontend
npm.cmd run lint
npm.cmd run build
npm.cmd audit
git diff --check
git diff --stat
```

Не публикувай при неуспешен build/artifact guard. При нов необходим файлов формат
прегледай риска и тествай промяната на allowlist; не изключвай цялата проверка.
Сканирай и repository/history за тайни с поддържан secret scanner; текущата проверка
разпознава само избрани шаблони и не доказва, че произволна парола липсва.

## Live проверка след deployment

- Сравни deployed commit и build log с проверената версия. Локален успешен build не
  потвърждава какво е качено на сървъра.
- Провери началната страница, albums/singles детайлите, mobile менюто, изображенията,
  външните listening линкове и airbrush Save PNG. Следи browser console за CSP грешки.
- Провери response headers на реалния хост: CSP с `connect-src 'none'`, без `unsafe-inline`
  и `unsafe-eval`; HTTPS/HSTS; `nosniff`; забрана за framing. Сравни с `render.yaml`.
- Провери `/admin/`, `/.env`, `/.git/config`, `/package.json`, `/appsettings.json` и
  `/Back%20End/MyApi/appsettings.Development.json`: не трябва да връщат частни файлове.
  Провери и тялото, защото catch-all страница може да върне HTTP 200. Не публикувай
  съдържание на намерени тайни в screenshots, отчети или чат.
- Потвърди липса на `.map`, backend binaries, admin bundle и локални credentials в
  артефакта. Не приемай липсата само на един guessed URL за пълен secret scan.
- Не поставяй private данни в `public/` или `data/temporaryContent.js`; и двете се
  използват за публично съдържание.

## Специално за REA и автоматизирано копиране

Преглеждай месечно официалните REA бележки за нови observation възможности. Не е нужно
да инсталираш REA за поддръжката. Ако тестваш собствен сайт, използвай отделен browser
profile без админ сесии/тайни; не отваряй публично CDP/debugging портове.

При реално scraping натоварване: разгледай edge rate limits и bot challenges, настрой
ги според наблюдавания нормален трафик и следи false positives. Ако има CDN отпред,
провери дали оригиналният provider URL не заобикаля ограниченията; ако не можеш да
ограничиш origin, не твърди, че защитата е задължителна за всички посетители.

Не разчитай на User-Agent блокиране на „REA“, robots.txt, забрана на десния бутон,
DevTools detection, CORS или обфускация за поверителност. REA може да работи с браузър,
който вече е получил файловете. Забраната на bots не отнема вече изтеглено съдържание.

## При инцидент

При непознат deployment/подменени файлове: запази logs и commit/deployment идентификатори,
ограничи достъпа, отмени компрометираните сесии/tokens, възстанови проверена версия и
провери акаунтите за устойчив достъп. При изтекла тайна я отмени/смени веднага; изтриване
от последния commit не я обезсилва. След отстраняване провери и history/cache/artifacts.
Само копиран дизайн не означава пробив в хостинга; не ротирай всички тайни без основание.
